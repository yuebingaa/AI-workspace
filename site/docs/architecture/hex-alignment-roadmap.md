# Hex 产品逻辑对齐与模块化改造里程碑

日期：2026-09-16。状态：**方案，未开始实施这些里程碑**。

本次只读取代码、核对公开资料并编写方案，不修改应用源码、数据格式或运行配置。当前已实现能力与启用状态的唯一维护入口仍是 [Agent 架构文档](./agent-architecture.md)；本文不能作为功能已经上线的证明。每个里程碑后续分别记录“源码完成 / 验证完成 / 开发站启用 / 稳定站发布”。

## 1. 改造目标与完成边界

目标是做一个以本地项目为基础、具有 Hex 类似分析流程的模块化数据工作空间，而不是复制其私有源码、云架构或品牌样式。

首轮产品闭环：

```text
本地项目与文件 → 数据目录 / 授权上下文 → 手工或 AI 编辑 Cells
             → 校验依赖并执行 SQL / Python / 转换
             → 可追溯的结果 → 表格 / 图表 / 文本
             → 用户确认采用 → 看板快照 → 保存、重开、继续分析
```

这张图是产品运行流程，不是源码依赖方向。源码边界见第 4 节。

保留现有 React / TypeScript、Next 路由约定及 vinext/Vite 运行方式；保留本地项目库、现有 Harness、DuckDB 与 Pyodide 适配、已有连接驱动、ChangeSet 和确认机制。先完成本地模式，不以配置外部数据库或购买服务作为验收前提。

首轮完成到 M7 为止；后续候选项单独列出，不在实施过程中无限追加。M1 是可靠性修复，M2 是以兼容为前提的重构，M3–M6 包含明确的新产品行为，不能把它们全部称为“功能不变的重构”。后续开发按里程碑逐个落地，不做全仓搬迁。

| 已核对的代码证据 | 已有能力 | 对后续方案的约束 |

| `core/datasets/server/dataset-repository.ts` | Dataset 仓库接口、描述和本地快照能力 | 接口与具体实现仍在一起，`rows` 路径仍有物化；不能宣称已有通用分页结果仓库 |

| `core/projects/state-repository.ts`；`core/notebook/dashboard.ts`；`core/changesets/` | 项目保存队列、修订冲突处理、Notebook 到看板的快照与变更确认 | 不增加第二份项目真相；快照不宣传为会自动刷新的实时 App |

| `core/architecture/module-boundaries.test.ts` | 已有运行时循环、客户端到服务端、执行器与持久化边界检查 | 扩展现有测试，不另引入重型架构治理框架 |

现有 Cell 类型是 `data / semanticQuery / sql / warehouseSql / python / transform / table / chart / text`。九种 Cell 的存在不表示 Hex 对应类型的全部交互都已经实现。

优先收敛的故障线索：

- 工具目录的 Schema 精简会移除部分约束，而执行端继续严格验证。必须核对 `createAnalysisPlan` 等工具的生成契约与执行契约，不能只让模型反复重试，也不能删除执行端校验来“修好”。
- [任务日志](../../../TASK-LOG.md) 最近的 Python 诊断记录了外层工具预算与环境准备、实际计算预算不匹配，以及生成代码的空值 / 重复计数口径问题。本轮未复现实验；它们是 M1 的复现输入，不是本轮新增验证成果。
- 当前有增量编辑 Cells 的工具路径，也有计划到 Notebook 草稿的路径。需要继续收敛，不能把“每次都重新生成整个 Notebook”当作默认交互。
- 手工执行与 Agent 获取原始工作簿的路径、生命周期不同。不能因为 Context 列出了文件名，就认为 Agent 已获准读取其内容。

## 3. 里程碑与验收门槛

按以下顺序实施。所有阶段当前均为“待实施”；本次方案核对只为 M0 提供输入，不代替测试基线。每阶段完成后提交一份可演示结果和验证记录，再进入依赖它的阶段。

| 阶段 | 交付物 | 用户能看到的结果 | 进入条件 |
| --- | --- | --- | --- |
| M0 基线与行为对照 | 选定的 Hex 行为清单、旧项目与合成数据样例、真实检查基线 | 明确做哪些、不做哪些 | 本方案 |
| M1 分析链路可靠性 | 工具契约一致性、分段预算、错误与统计口径测试 | 分析不再因已知契约缺失盲目重试；失败能定位 | M0 |
| M2 模块与 Cell 扩展边界 | Cell 目录、分离的编辑器 / 执行注册、窄数据契约 | 原有功能保持，新增类型不牵动整个 Harness | M1 |
| M3 结果访问与依赖执行 | 结果访问端口、显式依赖调度、失效与取消规则 | 修改上游后知道哪些结果要重跑，不把预览当全量 | M2 |
| M4 Agent 与 Cells 协作 | 共享业务用例、受控上下文、增量草稿与真实事件 | AI 修改指定单元、运行、验证，再等待采用 | M3 |
| M5 编辑器与基础交互 | 输入单元、统一的表格 / 图表 / 文本交互与渲染适配 | 可用参数驱动分析，手工和 AI 操作同一份 Notebook | M3、M4 |
| M6 本地项目闭环与功能删减 | 保存 / 重开、能力禁用、兼容加载、看板快照闭环 | 删除或关闭某项能力后，项目仍能安全打开 | M5 |
| M7 回归与开发站验收 | 完整验收记录、架构文档、替换说明与发布前清单 | 可稳定演示本地文件到图表的全过程 | M0–M6 |

### M0：冻结范围，建立可重复基线

- 对照本方案第 1 节的公开行为，逐项记录“文档依据 / 当前路径 / 差异 / 本阶段验收”。不是先采集全部 Hex 页面再开始开发。
- 复用现有测试体系；准备不含真实业务数据的 CSV / XLSX、旧格式项目、含空值与重复行的数据、超过预览行数的结果、被禁用的 Cell 样例。
- 核对工作区原有改动，执行第 7 节适用的现有命令；将原有失败、环境缺失和新增失败分开。未通过项不能仅写成“历史错误”而没有证据。
- 固定首轮范围：本地数据、现有九种 Cell、首批四种参数、现有图表类型、现有单表语义能力。暂不实现地图、Writeback、多租户、任意 pip 或完整云产品。

验收：形成可重复的基线和预期结果；不存在需要猜测业务含义的验收口径。当前工作区很脏，不能以清理未提交修改来建立基线。

### M1：先修稳真实分析链路

主要入口：`core/harness/tool-registry.ts`、`tool-schema.ts`、`analysis-plan-contracts.ts`、`runtime.ts`、`core/notebook/server/python-runtime.ts`、Notebook 执行器及相关测试。

1. 从同一个业务 Schema 生成工具描述并在执行端校验；供应商不支持的 Schema 关键字采用明确的适配和补充约束说明，不静默丢失规则。保留字段路径、期望类型 / 上限等结构化错误，禁止在错误中回显敏感输入。
2. 为已知的字段名、依赖数组与 `cellSearch` 参数失败建立离线回归。无效参数不触发执行副作用；只有可修复错误进入有次数上限的纠正流程。
3. 分开记录模型等待、运行环境准备、实际计算、结果转换。制定有上限且相互协调的 Notebook 工具预算；继续支持用户取消，不将“取消配额”解释为无限计算或无限重试。
4. 让失败时可查看草稿代码、失败阶段和安全错误说明，但不自动采用草稿、不输出敏感原始行。持久化失败草稿需复用项目范围与现有隐私规则。
5. 对“重复行是否计第一次”“纯空格是否为空”等口径使用显式定义和确定性样例；生成代码的结果必须与预期核对，不能仅以执行成功为准。

验收：离线模型替身驱动真实工具链，合法计划通过、非法计划准确报错；冷 / 热环境都能区分准备与计算耗时；取消不继续执行后续工具；合成数据计数正确。模型质量实测只能在另有明确授权与费用边界时进行，未做时写“真实模型端到端未验证”。

### M2：在已有模块上建立扩展边界

主要入口：`core/notebook/definition.ts`、`graph.ts`、`execution-contracts.ts`、`server/execution.ts`、`components/studio/notebook/`、连接查询契约和 Dataset 仓库。

- 建立小而明确的 Cell 能力目录：类型、配置 Schema、输入 / 输出种类、依赖提取方式、可用能力标记。目录不导入 React、驱动或模型客户端。
- 浏览器的编辑器 / 渲染注册与服务端的执行注册分开，按稳定 `kind` 连接；增加类型的入口明确，但不建设任意动态加载插件系统。
- 将执行器中的 Cell 专属计算逐步交给对应处理器；执行器仍统一管理依赖、取消、权限、追踪、结果状态。保留现有 `NotebookExecutionDependencies`，不要为每个普通函数制造接口层。
- 将可复用表结构和完整性描述归到 Dataset 业务契约；初期保留旧类型名的兼容导出，不改返回 JSON。数据库驱动不再从 Notebook UI/配额取得公共数据规则，连接自身的行数、超时限制仍由连接模块负责。
- Dataset 仓库端口与文件实现分开；项目持久化继续使用现有 `ProjectStateRepository / ProjectStateWriter`，不重复搭建仓库框架。
- 语义能力只做必要的兼容边界整理，遵循已有 [语义层设计](./semantic-layer-design.md)，不在本阶段混入新 Join 规则或权限口径合并。

验收：九种 Cell 的行为回归保持；用测试专用 Cell 处理器证明扩展无需修改 Harness 循环或模型适配；移除该处理器后能明确拒绝执行且其他类型正常；架构边界测试防止客户端引入服务器实现。

### M3：结果引用与依赖运行成为共同底座

主要入口：`core/notebook/contracts.ts`、`graph.ts`、`provenance.ts`、`server/execution.ts`、`core/datasets/` 和文件访问适配。

1. 区分“项目数据源描述”“单元定义”“运行结果”“可见预览”“完整数据访问”。优先在边界新增兼容端口，不要求所有内部计算立即改成流式。
2. 结果访问明确 Schema、来源、版本、完整性与权限范围；提供预览分页和受限物化能力。当前 `rows` 实现作为第一种适配器，大数据超限明确报错，不能靠把全部数据塞进浏览器假装解决问题。
3. 保留原 `resultRef` 证据语义；如果新增可读取句柄，明确项目 / 调用身份 / 数据授权范围、有效期和回收方式。过期引用要求重算，不能误读同名单元的旧数据。
4. 在现有显式依赖图上建立拓扑调度与失效规则：界面排序不作为唯一执行依据；缺失依赖、重复输出名、循环依赖均可解释。保留旧合法文档的运行结果。
5. 单独运行、运行到当前单元、全部运行共享调度用例；受影响下游标记过期。默认手动执行；参数自动重算仅在 M5 明确启用，并有合并更新、取消与预算控制。
6. 文件读取通过受控文件访问端口，手工与 Agent 共用解析能力而保留各自授权判断。禁止从模型提供的任意绝对路径读取文件。

验收：超过预览大小的数据聚合仍基于完整可用输入；不完整输入拒绝伪全量计算；修改上游只使相关下游失效；失败或取消不得复用旧结果冒充新结果；两个项目、人工 / AI 数据策略之间不串结果；日期、时区、空值、大整数与小数精度有边界样例。

本阶段不实现远端 Query mode，不自动下载无限大数据，也不宣称支持分析任意 Python 代码中的隐藏依赖。

### M4：让 Agent 操作同一套 Notebook 能力

主要入口：`core/harness/notebook-cell-tools.ts`、`notebook-cell-search.ts`、`input-inspector.ts`、`runtime.ts`、`app/api/ai/harness/handler.ts`、`core/ai/server/`。

- 让普通 API 与 Tool 调用同一份“查单元 / 编辑草稿 / 执行 / 获取结果 / 提交草稿”业务用例。Tool 只做参数、身份、业务调用与结果转换，不复制 SQL、图表或数据变换算法。
- 简单解释只读上下文；局部修改走现有增量 Cell 路径；复杂多步任务可走 `createAnalysisPlan`。保留计划能力，但不让不需要计划的任务被强制挡在规划门槛。这是本项目目标，不是对 Hex 私有实现的断言。
- 保留意图判断后按需启用 Input Inspector 的现有方向；Context 提供目录、选中对象、版本和受控摘要，不默认包含整本 Excel。
- 模型提出行动，工具执行和验证，SSE 展示真实结构化事件。取消、断流、失败与重试显示实际状态，不展示或伪造模型内部思维链。
- 采用草稿必须匹配当前 Notebook / 项目版本；未经用户确认不修改正式看板。聊天记录、工作记忆、任务证据与正式文档分开存放。

验收：选中一个 Cell 的修改不会重写其他 Cell；失败草稿可检查但未采用；跨项目会话不读到另一项目上下文；模型替身可以替换真实模型跑同一套工具用例；既有 API 和 SSE 消费端通过兼容测试。

### M5：完善 Cells 编辑器与基础交互

主要入口：`components/studio/notebook/`、`NotebookResult.tsx`、`components/data-components/`、Notebook 契约、图表配置边界及样式。

- 统一 Cell 的名称、编辑、运行、取消、结果、错误、过期与折叠交互；采用“共用外壳 + 类型专属编辑器”，不把所有类型代码重新塞回主面板。
- 首批加入文本、数字、日期、单选参数；保留运行按钮作为执行触发。参数到 SQL / Python / 图表依赖是结构化绑定，不对输入值做可执行字符串拼接；远端驱动未具备参数绑定时明确不支持，不降级为不安全插值。
- 结果重命名更新受支持的结构化引用；遇到不能可靠改写的自由 Python / SQL 代码，提示待检查，不靠正则声称已安全修改全部依赖。
- 表格的分页、排序与导出明确是“完整可访问结果”还是“当前预览”。图表字段、聚合与配置独立于 Recharts 渲染；先保留现有图表能力，再按真实需求增补。
- 文本引用受控的参数和结果字段，禁止通过文本模板执行任意代码。保留简单静态文本兼容。
- 将选中的参数 / 数据 / Cell 加入上下文的菜单统一到现有元数据访问入口。新增工作界面仍为空白，不自动塞入示例看板。

验收：用户能完成“参数 → SQL / Python → 表格 / 图表”的本地分析；启用参数自动重算后只更新受影响链路；1024 px 与常用桌面宽度检查布局、键盘操作、焦点和错误提示；同步视觉规范。手机适配不是本阶段范围。

## 5. 如何保证以后可以增加、关闭和删除功能

### 增加一个功能

以未来新增 Pivot Cell 为例：增加配置 Schema / 稳定类型、依赖声明、对应计算处理器、编辑器、结果展示与测试，再接入浏览器和服务端各自的注册表。只有实际存在数据聚合差异时才扩展业务用例；不为一个 Cell 修改模型供应商 HTTP、Harness 循环或项目保存队列。Pivot 本身不属于首轮必须交付的功能。

允许少量有意义的中心修改，例如扩展类型联合、Schema 或注册表；目标是减少联动，不承诺任何功能“只加一个文件、完全零改动”。共享目录只放稳定描述，不把服务端实现通过统一 `index.ts` 导出到前端。

### 关闭与移除分开处理

1. **关闭入口**：能力目录同时控制 UI 可创建类型、Agent 可用工具 / 能力描述、服务端执行许可；只隐藏按钮不算关闭。能力开关不能替代授权检查。
2. **保留项目**：已保存的禁用类型显示只读占位、原配置和依赖说明，不执行；恢复能力后可继续使用。其下游标记阻塞，不偷偷换算法。
3. **兼容未知类型**：项目读入层可以安全保存带版本的原始定义，执行层仍严格验证已支持类型；“可打开”不等于“允许执行任意内容”。未知类型不能导致整份项目被自动清空或重写。
4. **真正移除代码**：先检查类型、注册、动态加载、API、数据依赖和旧项目；有迁移需要就提供备份和显式迁移。无法安全迁移时保留小的只读兼容器，不删除数据。
5. **移除验证**：测试该能力缺席时其他功能继续可用，客户端 bundle 不拉入对应服务端依赖；检查旧项目能打开，API 明确返回不支持而非 500。

这套机制是目标实现，当前并不具备完整的未知 Cell 兼容加载。实现时不得以放宽所有 Zod 校验来替代分层的读取与执行校验。

### 将来替换具体实现的主要位置

| 替换项 | 主要修改位置 | 必须保留或明确的差异 |
| --- | --- | --- |
| 模型供应商 | `core/ai/server/` 新适配 + `harness-composition.ts`；遵守 `HarnessModel` | 工具调用、图片、流式输出、取消与用量能力；缺失能力明确拒绝或走已声明路径 |
| 外部数据库 | `core/connections/server/drivers/`、驱动选择 / 配置适配 | 方言、类型、认证、取消、分页、只读权限；不将数据库权限复制到模型提示词 |
| 本地 Python / SQL 引擎 | `NotebookExecutionDependencies` 的实现与 `server/runtime.ts` 组装 | 环境准备、包能力、时间 / 内存、数据类型、结果完整性和取消 |
| Agent 策略 | `core/harness/` 中规划 / 路由模块及对应组装 | Tool 名称与参数兼容、验证证据、草稿确认，不直接更改执行器或数据库 |
| 图表库 | M5 的 renderer 适配及其配置映射 | 交互、坐标、聚合、空值和图表能力可能不同，不能承诺换库后像素完全相同 |
| 项目 / Dataset 存储 | 各自仓库端口的具体适配与组装 | 版本冲突、迁移、删除 / 回收语义；不在 React 组件中替换文件系统代码 |

## 6. 状态与数据所有权

| 状态 | 所有者与生命周期 | 明确禁止 |
| --- | --- | --- |
| Notebook / 语义定义、页面布局 | 项目状态与版本化保存入口；只有确认的变更进入正式状态 | Tool、UI 和执行器分别维护互不一致的正式文档 |
| 导入文件、Dataset、数据目录 | 项目文件 / Dataset 仓库及授权元数据适配 | 用文件名称冒充权限；删除 Dataset 时无提示地销毁原文件 |
| 单次运行、取消、结果证据 | Notebook 执行与结果访问；区分临时结果和显式保存的数据 | 把上次成功结果当作这次失败任务的输出 |
| AI 草稿与任务状态 | Harness 任务 / 草稿机制，带基础修订和运行身份 | 绕过用户采用，或用旧草稿覆盖较新的项目 |
| 聊天历史、摘要、工作记忆 | 现有会话存储，按项目 / 会话隔离 | 因 UI 显示历史，就假设模型已收到或有权读取全部文件 |
| 选中对象、展开、宽度、编辑中输入 | UI 局部状态；需要恢复的部分经明确项目适配 | 将组件引用、浏览器对象或服务器凭据写入项目文件 |

任何结果缓存即使第一版只有本地用户，也必须携带项目与访问范围；人工和 AI 的结果策略不一定相同。复用公共执行能力，不等于合并两类权限或掩码行为。

### 每阶段共同的完成标准

- 旧行为或明确新增行为都有确定性断言；手工和 Tool 入口调用同一业务实现。

- 无新增运行时循环；浏览器依赖图不触达私密模型实现、文件系统或数据库 SDK；核心规则不依赖 UI。
