> 后续源码复核更正（2026-09-29，架构方案任务）：下文第 3 项的关键词 Schema 裁剪仅能证明旧 Harness 的 `createNotebookDraft` 行为。当前主工作台 DSH 的 `editNotebookCells` 通过 `core/harness/server/notebook-tool-bridge.ts:68` 从 canonical schema 生成目录，仍包含 GW 配置。因此“普通 AI 默认拿不到新版图表配置”不能泛指 DSH 主工作台，也不能在没有真实模型实验时断言其默认产物必然走旧图。架构应统一两条路径的生成约定；详见[后续方案](../architecture/visualization-unification-proposal-2026-09-29.md)。保留下文原审查供追溯，此更正优先。

## 结论

不需要因为这些差距马上更换 Graphic Walker。当前主要问题是：两套图表语义并存，AI 默认产物与新版编辑器没有统一，新版图到看板的出口未接通，文字结果没有按报告阅读方式呈现。已经有 Notebook、SQL/Python、参数联动、实时草稿预览和确认/撤销，不能再归为“没有做”。

## 做错了或存在明确体验缺陷

### 1. 分析结论以 Markdown 原文显示，而非可阅读报告（P1，界面与代码确认）

本地 Notebook 的“分析结论”直接显示 `##`、`**`、引用符号和管道表格；同一页右侧聊天却正常排版。结果进入正式分析文档后可读性反而下降。

代码：`components/studio/notebook/NotebookTextResult.tsx:8` 直接把 `cell.markdown` 放进 p；第 18 行引用结果也是纯文本。这里是有意采用纯文本实现，并非 Markdown 库损坏，但与 AI 生成 Markdown 的输出约定不一致。

建议：统一受限 Markdown 渲染，支持标题、段落、列表、表格、引用；禁止原始 HTML，并保留引用结果的新鲜度检查。验收同一结论在聊天与 Notebook 的结构一致。

### 2. 排序被写死，排名图缺少正确的表达能力（P1，代码确认，运行效果待专项复现）

`core/chart-editor/config.ts:89` 对字段引用统一写入 `sort: "ascending"`，配置模型没有按指标降序或保留输入顺序的选项。不能把 SQL 已排好的 Top N 当作图上顺序必然保留。

建议：明确分类排序、按指标排序、输入顺序三种策略。用分类名称顺序与数值排名相反的样例验收，不能只用天然按季度升序的销售样例。

## 做偏了：局部成立，整体流程未统一

### 3. AI 默认仍偏向旧图，新版交互不是默认产物（P1，代码确认）

`core/harness/tools/parameter-projection.ts:430` 的 createNotebookDraft schema 投影，仅在文档已有 GW 图或请求明确提到 Graphic Walker 等条件下保留 `graphicWalker`。普通新文档“按季度和客户类型画图”请求不会自然获得完整新版配置契约。

这不代表 AI 完全不能生成 GW；现有测试明确覆盖启用条件。但用户不应知道底层库名称才能获得新版体验。

建议：按图表需求启用统一配置；例如需要颜色分组、日期粒度、分面时提供相关字段。继续做 schema 精简，但不要把品牌关键词作为主要产品开关。先验收常规自然语言能生成可继续编辑的新版图。

### 4. 同类图表在编辑前后可能采用不同数据语义（P1，代码确认）

`NotebookChart.tsx:16–17`：有 GW 配置走新版；旧图只画前 100 行。`core/notebook/graphic-walker.ts:17` 将旧单指标图转为默认 sum；新版 `graphicSpec` 固定 `aggregate: true`，基于已载入输入重新聚合。多指标、饼/环形图则继续使用兼容编辑器。

重复分类的旧图保存到新版后，可能从多条原始记录变为分类汇总；同时可绘制的数据范围也可能变化。代码已有迁移提示和旧图截断提示，所以不能指责为完全静默丢数据，但提示不能替代统一语义。

建议：迁移先比较原始/聚合口径，明确保留明细还是汇总；统一各类型的字段、筛选、格式契约，再逐步替换渲染器。不要为追求一个渲染库强行删掉旧图能力。

### 5. 图表输入、图上聚合结果、可复用结果是三个不同对象（P1，代码确认）

`core/notebook/presentation-table.ts` 只投影输入字段；`ChartCanvas.tsx:27` 在浏览器对 dataset.rows 计算；`NotebookResult.tsx` 已明确“输入数据”与图内聚合结果的区别。保存 Dataset 保存的是输入，不是图上聚合结果。

当前防误导说明是正确的，但如果用户想继续分析图上汇总数值，还要另写 SQL 或转换步骤；不能仅因单元执行成功，就认为服务端已产生了图上聚合结果。

建议：确立统一结果协议，区分 inputResult 与 visualResult，保留筛选、聚合、数据版本及完整性信息。先打通可复用的图表计算结果，再做跨图联动和 AI 引用。大数据查询下推属于后续工程，不应把浏览器预览当全量分析。

## 没有做完

### 6. 新版图不能进入看板（P1，明确阻断）

`core/notebook/dashboard-policy.ts:24` 对 `cell.graphicWalker` 直接返回不支持。Notebook footer 也隐藏快照入口并提示导出图片。这是合理的临时防损失保护，但业务上“编辑图 → 放到看板”没有闭环。

建议：看板复用同一图表定义和渲染边界，选择明确的快照或动态结果策略，不把 GW 降级转成丢失分组、筛选、样式的旧图。若只交付单图阶段，可暂缓；若目标是 Hex 式 Notebook → App，则必须补齐。

### 7. 透视分析与读图配置还不完整（P2，配置模型确认）

- Y 轴只接受数值字段（`config.ts:45`），无法直接拖字符串订单号做计数/去重计数，尽管聚合列表中列出了 count/distinctCount。
- 新版每轴只一个字段，不支持多度量；Notebook 新版仅柱/线/面积，散点仍限独立编辑器；饼/环形、多指标走旧编辑器。
- 数字格式只有整数、两位小数和百分比，缺少独立轴标题、货币/万/百万单位及每个指标自己的格式。实际 /charts 显示 `quarter(季度)` 和 `sum(成交金额)` 这类计算表达式轴标题。
- `ChartCanvas.tsx:78` 固定 light，主题 light/dark 同值，尚未真正实现图表明暗主题。
- Tooltip 分类字段接入 details，会细分聚合粒度；界面已有说明。若产品把它叫单纯“提示信息”，应拆成分组字段与提示字段，避免用户以为只影响显示。

### 8. 嵌入后空间与操作层级还需整理（P2，代码与界面观察）

Notebook 内仍嵌入字段库、配置、画布三列，加上页面大纲和 AI 侧栏；局部 CSS 使用 680px 编辑高度、590px 输出高度，窄容器才隐藏字段库。不是完全没有响应式，而是对 Notebook 同时读步骤和读图的场景还不够紧凑。

图表保存更新定义，但 `useNotebookAutoRun` 的 approvedSave 基于 parameterValueChanges；不能把参数自动重算等同于图表保存自动更新正式结果。编辑预览 → 保存定义 → 正式运行仍需明确连贯的反馈。

建议：默认精简图表工具条，字段库按需打开，提供放大编辑；对纯样式变更即时更新，对查询语义变更明确运行状态。验收 1366px 且 AI 侧栏展开的真实使用场景。

## AI 呈现流程对照

Hex 当前项目可观察到：问题/上下文 → 数据查询单元 → 命名结果 → 引用结果的图表/KPI → AI 解释与单元引用 → 待确认修改；已有 App 视图承载多个结果。此次未新跑 AI，不断言其内部实现。

我们源码已具备：AI 计划/工具 → SQL/Python 等执行 → 实时只读过程与结果 → 草稿试运行 → 整体确认/撤销。`NotebookLivePreview.tsx` 与 `NotebookDraftReview.tsx` 能证明这条链已存在。主要缺口位于最终可编辑图表、图上计算结果复用和看板承接；逐单元确认也不能和现有整体确认混为一谈。

## 建议顺序与验收

1. 修复文字结果排版，补排序规则；用真实分析结论、逆序排名样例验证。
2. 统一 AI 与手动编辑的图表契约，验证“按季度、分客户类型画图”无需提库名即可得到可编辑分组图。
3. 统一旧图迁移和聚合结果语义，覆盖重复分类、NULL、超过 100 行以及已截断上游。
4. 按产品范围补看板承接，确保编辑结果完整保留；此后再补多度量、透视计数、主题与读图细节。

不建议重新堆一套 Notebook 或 AI 框架，也不建议先更换图表库。先修上述链路，才能检验当前组件是否真正不够用。
