# DataCanvas 与 Hex 录屏对比：优先修复分析过程的衔接

日期：2026-09-27。状态：录屏与源码诊断、改造建议；未修改网站实现。

2026-09-28 实施补充：已按本文第一批范围接入实时草稿、逐单元进度和有界结果、官方 DSH 过程列表与单元定位，保留最终核验和人工确认。以下诊断保留为改造前证据；当前实现与验收边界见[实施报告](../verification/notebook-live-progress-2026-09-28.md)。第二批布局与后续运行时 / 缓存扩展不在本次范围。

## 判断

当前最值得优先投入的是：让 AI 的每一步工作及时出现在 Notebook 中，并让聊天、单元格和运行结果表达同一件事。已有数据读取、SQL、图表、代码编辑器和结果表应继续复用。

录屏中的 DataCanvas 已经能交付分析表图，但生成过程主要发生在用户看不见的阶段。单纯继续增加单元类型、设置页或更换组件，无法消除这段等待。后续改造应围绕一个完整用户任务验收。

## 已由当前源码确认的衔接问题

### 1. 前端有事件流，但事件流没有把正在形成的 Notebook 投影出来

[`components/studio/workspace/assistant.ts`](../../components/studio/workspace/assistant.ts) 的 `onEvent` 更新任务状态、计数、耗时和 trace；没有在这里更新草稿单元或单元结果。

[`components/studio/StudioWorkspace.tsx`](../../components/studio/StudioWorkspace.tsx) 的 `notebookDraft` 只选择 `awaitingConfirmation` / `completed` 任务的 `notebookArtifact`。`onNotebookDraftReady` 再触发隔离预览运行。

[`core/agent-engines/server/dsh-engine.ts`](../../core/agent-engines/server/dsh-engine.ts) 已发送工具开始、完成和失败事件，但草稿是在最终核验通过后才挂到任务的 `notebookArtifact` 上。这与“前面空白，后面整批出现”的画面一致。

因此不能把问题简单归为“没有 SSE”。现有流式通道需要增加受版本约束的草稿与单元进度，而不只是流式输出文字。

### 2. 聊天界面只收到最新一条状态，完整工具轨迹没有作为过程列表传入

[`components/studio/AiBuilderAssistant.tsx`](../../components/studio/AiBuilderAssistant.tsx) 传给 `DshWebFrame` 的 `statusText` 来自 `trace.at(-1)?.message`。

[`runtime/dsh/web-client.mjs`](../../runtime/dsh/web-client.mjs) 把运行状态放在输入区附近的一行文字中，并对超长文字省略显示。仅替换聊天组件，并不会自动把现有工具事件变成 Hex 那样的过程卡片。

### 3. 生成阶段的执行证据和前端预览是两次不同的状态推进

[`components/studio/notebook/NotebookDraftReview.tsx`](../../components/studio/notebook/NotebookDraftReview.tsx) 已区分“生成阶段试运行通过”和当前预览。

[`components/studio/notebook/NotebookPanel.tsx`](../../components/studio/notebook/NotebookPanel.tsx) 发起预览运行后统一接收 `body.run`，运行中的单元统一显示“等待结果”。这可以解释右侧已有分析说明、左侧仍等待本轮结果的体验。

重跑可能承担版本、上下文和权限校验，不能未经验证就删除。目标是让结果身份可关联：同一版本且仍有访问权时考虑复用已经校验的结果；确实需要重跑时清楚显示原因和当前阶段。

## 下一轮应怎样改

### 第一批：让一个分析任务从开始到完成都看得见

仅以“上传一个 Excel → 查看字段 → 按工站汇总 → Top 10 图 → 修改为 Top 5”为交付主线。第一批无需覆盖 Hex 的全部功能。

1. **保留过程列表。** 显示“已读取工作表”“正在生成工站汇总”“查询失败，正在修改”“图表已生成”等实际事件；每步关联目标单元。技术工具名收进详情，不能用计时器伪造进度。
2. **逐步显示草稿。** 服务端创建或修改一个单元后，经现有事件通道发送草稿更新；前端立即在 Notebook 中显示明确标注的草稿。生成期间仍可查看已有内容。
3. **单元状态就地更新。** 区分待生成、排队、运行中、成功、失败、已失效与已取消。一个单元失败时，显示实际错误及受影响的下游；不要把所有单元都显示成同一种等待。
4. **把结果接回对应单元。** 逐个接收已验证的执行结果引用和有界预览，图表绑定对应表结果。最终结论引用本次成功结果；存在未解决失败时明确表示部分完成。
5. **保留现有采用 / 撤销机制。** 实时展示可以发生在保存正式文档之前。先沿用整稿确认；逐单元确认涉及依赖一致性，可作为后续批次。

实现入口：`dsh-engine.ts` / Notebook 工具桥 → 事件契约及流式客户端 → `workspace/assistant.ts` → `StudioWorkspace.tsx` / `NotebookPanel.tsx`；聊天 Frame 单独增加过程列表映射。

事件必须携带所属任务、单元、草稿版本和运行身份；切换项目、取消任务或接收过期结果时，不能把旧内容填入新工作区。不要直接把工具的全部内部状态或原始数据塞入事件流。

### 第二批：收紧阅读与编辑体验

- 继续使用当前暖白、黑白灰视觉，保留已接入的 CodeMirror、TanStack Table 和图表组件。
- 把标题、代码、结果组织成稳定的单元结构，减少重复状态和辅助段落。高级导出说明、运行详情默认收起，但截断范围等影响理解的信息仍须可见。
- 聊天面板支持拖动宽度；先在 1680 宽视口试验 360–420 CSS px，再验证 1024 宽布局。录屏缩放、DPI 和浏览器缩放未核验，不按视频像素直接推导 CSS。
- 正文以易读为目标调整字号，避免关键说明与次要元信息同等细小；不要把所有控件同时放大。
- 排名图显示完整业务标签、指标名称和单位，例如“累计报警时长（分钟）”；代码字段名如 `cnt` 留在数据详情。图表类型根据数据选择，不能仅为模仿配色改图。
- 新输出出现时允许定位到对应单元；用户已向上阅读时不强制拉回底部。

### 后续：能力和性能扩展

第一条主线稳定后，再评估分组配色、堆叠图、逐单元确认、依赖增量重算、结果缓存和更多连接器。是否更换 Notebook 运行时，应以迁移样板的真实验证决定；本次证据不足以支持推倒当前实现。

## 验收应从“功能存在”改成“整段操作通过”

使用同一份合成 Excel、同一条问题、相同视口录制完整过程，分别验证：

1. 提交后立即出现真实的已接收 / 处理中状态；首个草稿单元在事件到达后显示，不等待最终回复。
2. 过程列表与单元状态一致，表图能够对应到实际执行结果。
3. 人为加入可修复 SQL 错误，看到失败位置、修改与重试；重试仍失败时准确停止，不伪造成功。
4. 中途取消后，不再插入迟到的单元或结果；已保存内容可继续查看。
5. 将 Top 10 改为 Top 5 时，能看清修改对象和对应输出；需要重算哪些上游由依赖关系决定。
6. 采用、撤销及重新打开项目后，正式定义与结果版本不混淆。

记录从提交到首条状态、首个单元、首份结果与最终完成的耗时，再定位模型、工具和前端各自的等待。当前两段录屏不能充当这些性能指标。
